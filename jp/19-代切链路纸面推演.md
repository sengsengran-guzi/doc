### K1 · 支付单超时后仍可付款（P1）+ 代切继续支付（P2）

**现状（已核实代码）**：
- `GzPayTransactionServiceImpl.createOrderInternal`：`expire_time = now + 5min` 只存本地；`UnifiedOrderRequest` 没有 `time_expire` 字段，微信侧支付单按默认有效期（远长于 5 分钟）。
- `GzLocalPayScheduler.payExpire` → `markTimeout`：只把本地 `status` 改成 `timeout`，**不调** `closeOrder`。
- 回调 `handlePaymentNotify`：只在 `status=paid` 时判重复，其余走 `applyPaid` → `markPaid … WHERE status='pending'` → affected=0 → 记成 `duplicated` 返回成功。
- 主动查单 `reconcilePaid` 同样只处理 `pending`。
- ⇒ 客人在收银台停留超过 5~10 分钟后付款：**扣款成功、订单不变、没有任何告警**。拼豆 / 回收 / 拼团都走这条链路。

**建议**（D7 新增一张 GZ-PAY 卡，先于 GZ-JP-110）：
1. 统一下单带 `time_expire = expire_time`（微信侧到点自动拒绝付款）——只新增参数，不改既有方法签名；
2. 回调或查单发现「微信说已付款、本地已是 timeout / closed」→ 不吞：写 error + 记一条待处理（admin 可见），由业务方决定补单或原路退款；
3. 上线前用 prod 库查一次历史上有没有已经被吞掉的单（`gz_pay_callback_log` 里 `duplicated` 且对应交易非 paid）——**需要你授权连 prod**。

代切的「继续支付」（P2）依赖第 1 条：同一客人对同一件商品再次提交时，返回他自己那张未付款订单并重新下发支付参数
（原支付单仍在有效期内就复用，已过期就新建一笔），而不是被自己的锁挡住。

**要你定的**：动共享支付通道（拼豆 / 回收线上在用）修这个洞，做不做、现在做还是单独排。我的建议是做、放进 D7。

### K2 · 煤炉 Shops 商品卖不卖（P8）

煤炉搜索结果里混着两类商品：个人卖家（`m…` 开头）和煤炉 Shops 企业店铺（另一套 ID，下单页不同）。
Shops 多是新品、库存稳定、一般包邮，但自动下单要另外适配，技术验证也要多验一种。

## 2. 场景推演

记号：C 客人 · R ruoyi · G 日本服务 · M 煤炉 · W 微信支付 · S 日本员工 · D 国内店员。
钱账四列：客人实付 / 已退客人 / 煤炉花费 / 甲方毛收入（实付 − 已退 − 煤炉花费，未计运营成本）。T = 到手价，E = 到付预估运费。

### S1 正常自动成功（包邮）

| 步 | 动作 | 状态变化 |
|---|---|---|
| 1 | C 搜索 → R 归一化 → G 搜索 → R 过滤 + 翻译 | — |
| 2 | C 进详情 → R 实时查 → upsert `snap_item`，准入 auto → 报价 Q（10 分钟） | `snap_item.gate_result=auto` |
| 3 | C 立即购买 → 确认页勾选 → 提交：校验 Q → **实时复查一次（P4）** → `FOR UPDATE` 锁 → 建单 → 拉支付 | 订单 created、行 purchasing、`active_order_item_id`=该行 |
| 4 | C 付款 → W 回调 → GZ-PAY paid → jp onPaid 同事务写任务 | 订单 paid、任务 queued |
| 5 | 5 秒内调度取任务 → 选账号 → G 下单（核价 → 点击 → 交易页） | 任务 success、`trade_status=await_ship`、行 `await_seller_ship` |
| 6 | 巡检：卖家发货 → shipped；S：已到仓 → 验货通过 → 煤炉评价 → 已评价 | `trade_status=rated` |
| 7 | D 在履约看板按一期流程推进到 delivered | 行 `delivered` |

钱账：T / 0 / 商品日元价 / T − 商品价。客人「1 分钟内看到已抢到」：回调到 G 返回约 10~40 秒，✅。

### S2 被抢 / 下架 / 涨价（自动下单前发现）

步 1~4 同 S1；步 5 G 核价发现售出 / 下架 / 当前价 > 锁定价 → **没点购买** → `failed`。
R：任务 failed → 行 purchase_failed → 一期行级退款 T → 释放锁 → 退款回调 → 行 refunded、订单 refunded。
钱账：T / T / 0 / 0。✅ P4 修完后，「报价之后、付款之前」被买走的情况在步 3 就被拦下，不会走到这里。

### S3 降价

步 5 当前价 < 锁定价 → 照买，`actual_price_jpy` 落库。钱账：T / 0 / 实际价 / 多出的差价归甲方。✅（REQ-SNAP-028）

### S4 准入转人工（「コメント必須」，包邮）

步 3 准入 manual（详情页已提示）→ 付款 → 回调写任务 `manual_pending`（`gate:kw:コメント必須`）。
S 在采购账号上留言沟通 → 手工下单 → 后台「填成功」（交易号 + 实际价）→ 与 S1 步 5 同一出口。
卖家要求加价：**实际价 > 锁定价时不能填成功**，只能「填失败（涨价）」→ 全额退款（P13，与自动一致）。
谈不成：填失败 → 全额退款 + 释放锁。客人等不及要取消：找客服 → S 填失败（P14）。
钱账：成功同 S1；失败 T / T / 0 / 0。✅

### S5 到付商品（着払い）

步 2 准入 manual（`shipping:buyer`），报价含 E → 实付 T（含 E）→ 人工队列 → S 手工下单 → 填成功（交易号 + 实际价，**此时不填运费**）。
货到转运仓：S 点「已到仓」时填实际运费 A 日元（P3）→ 差价 = E − ceil(A × 锁定汇率 / 100 × 100 分)：
- > 0 → 发起 `shipping_diff` 部分退款，回调**不改**行与订单状态（订单仍 paid）；
- ≤ 0 → 不补收，甲方承担。

之后验货不通过退货：退款额 = T − 已退差价（不超退）。
钱账（差价 d > 0）：T / d / 实际价 + A 换算 / T − d − 成本。✅
**前提要甲方确认**：转运仓接收到付件。不接收 → 到付商品应在准入时判 blocked（不可购买），整条到付逻辑可以不用。

### S6 卖家取消 / 交易被取消（含已发货后丢件、事务局取消）

成功后巡检发现 cancelled，或 S 手工标记「交易取消」（**允许从待发货或已发货出发**，P9）→
任务 fail_reason=seller_cancel → 行 await_seller_ship → purchase_failed（**走系统内部方法，不经过 admin 守卫**，P10）→
退款 T − 已退差价 → 释放锁。煤炉侧货款退回采购账号余额。
钱账：T / T / 0（煤炉退回）/ 0。✅

### S7 验货不通过

已到仓 → S 在煤炉走退货 → 后台「退货完成」→ fail_reason=inspect_ng → 行 purchase_failed（内部方法）→ 退款 T − 已退差价。
钱账：T / T / 实际价（若卖家同意退款则退回）/ 0 或 −退货运费。✅（REQ-SNAP-033：客人退款不以卖家退款为前提，甲方承担纠纷风险）

### S8 结果不明（三种故障）

| 故障 | 推演 | 结果 |
|---|---|---|
| G 点击后超时（45 秒） | R 记 unknown → +30s 对账：购买记录可能还没出现 → 商品已是「交易中」→ **不判失败、继续等**（P5）→ +2min / +10min 再查 → 查到 → success | 自动成功，客人约 2~12 分钟看到结果 |
| R 与 G 之间断网 | 同上；若 3 轮都查不到（或对账调用本身失败）→ 人工 | 人工确认 |
| R 进程在执行中重启 | 启动时 `executing` 超 60 秒 → unknown → 对账 | 同上 |

全程**没有**第二次 `POST /v1/purchases`、**没有**退款。钱账在落终态前：T / 0 / 未知 / —。✅（REQ-SNAP-039）

### S9 风控（验证码 / 登录失效）

G 返回 unknown + risk_signal → R：该账号 challenge、总开关关、所有 queued → manual_pending（auto_paused）；这一单进对账，
对账依赖登录态会失败 → 3 轮后人工。S 通过远程登录工具（P12）在东京服务器的浏览器里重新登录（含短信验证）→
心跳 healthy → admin 手动恢复总开关（需有健康账号）。人工队列里的单不会自动回到自动队列。✅

### S10 账号余额不足（P6）

G 在购买页识别「残高不足 / 支払い方法エラー」→ **没点购买** → `failed(account_unpayable)` →
R：不退款，任务转人工（`account_unpayable`）+ 停用该账号（pause_reason）+ 告警。其他健康账号继续；都不可用 → 新单 `no_account` 转人工。✅

### S11 未付款 / 收银台取消（P1 / P2）

| 时间 | 现状（K1 不修） | K1 修后 |
|---|---|---|
| 0 | 提交，锁商品，拉收银台 | 同左，支付单带 time_expire = 5 分钟 |
| 1 | C 关掉收银台 → 订单 created（死单）；C 再点购买 → **被自己的锁拦住** | C 再点购买 → 返回原订单 + 新的支付参数，可以继续付 |
| 5~10 | GZ-PAY 本地标 timeout，微信侧仍可付 | 微信侧已过期，付不了 |
| 7 | C 若此时付款 → **扣款成功、回调被吞、订单不变** 🔴 | 不可能发生 |
| 15~20 | GZ-JP-110：查单 → 微信说已付款 → 「按回调补处理」又因本地非 pending 被跳过 → **永远不关、锁永远不释放** | 查单未付 → closeOrder → 关单 → 释放锁 |

### S12 两人抢同一件

A、B 同时提交 → `FOR UPDATE` 串行 → A 建单，B 收到「已被其他用户下单」。A 15 分钟内不付 → 关单释放 → B 可重新下单。✅

### S13 小程序被刷（P11）

匿名脚本每秒大量搜索 → 缓存挡住同词，换词就打穿 → G 全局令牌桶耗尽 → 真实客人 429。
修：R 侧按用户（未登录按 IP）限流，超限直接返回「搜得太快了」，不消耗 G 的额度。✅
