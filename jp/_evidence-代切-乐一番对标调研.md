# 取证 · 代切（煤炉）对标调研 ——「参考乐一番的实现」到底指什么

> 2026-09-26 主线程实搜（web 每条带出处）+ 代码逐处核对（带绝对路径）。
> 起因：甲方反馈「煤炉的 API 拿不到，参考乐一番的实现」。代切属**二期**（`doc/16` §附录二 / `requirements.yaml` REQ-SNAP-001..010 全部 `deferred`），本文件只做调研，**不排期、不做商业判断**。

## 0. 三句话结论

1. **乐一番（乐淘一番）不是「贴链接代拍」工具，而是一套完整的自建代购商城**：站内搜/逛煤炉 + 购物车 + 人民币支付（自动换算汇率）+ **支付后系统「秒切」自动下单** + 失败全额退 + 人工代买兜底；商品图走它自己的 CDN（`image2.leyifan.cn`）。
2. **它敢这么做的原因是它自称 Mercari 官方合作伙伴、用「煤炉官网认证账号（楽一番*）」下单**；其官方 FAQ 里还自陈「**平台提供的 API 对接功能并未完善**」——即**官方合作是有 API 的**，只是不给自助申请。甲方说的「API 拿不到」，真实含义是**没拿到合作资格**，不是「煤炉没有 API」。
3. 所以「参考乐一番」有两种完全不同的解读（**商务路径** vs **产品形态**），对应的排期与成本差一个量级 —— 这是开工前**必须让甲方各回一句**的第一件事（见 §4）。

## 2. 乐淘一番的煤炉代切：产品形态（可抄的部分）

### 2.1 三种找货入口，两条数据路径

| 入口 | 怎么拿数据 | 说明 |
|---|---|---|
| **站内搜索框** | 自建商品索引 | 「搜索框可输入心仪的商品关键词**或商品 ID**」（[切煤教程](https://m.55haitao.com/show/312459/)）；「可通过搜索框直接搜索商品（目前**仅支持中文、日文**搜索）」（[煤炉站点购物指南](https://letaoyifan.com/article/id/376)）。运营侧还会直接教用户贴日文关键词（「煤炉日语搜索关键词：SEVENTEEN…」），说明**中文搜索靠翻译/映射兜底，日文搜索才是主路径** |
| **贴链接** | 单次抓取 | 「可通过复制黏贴 Mercari 日本（jp.mercari.com）网站商品的详细链接，**直接跳转至该商品**，进行购买」——同页（官方指南） |
| **Chrome 插件** | 在煤炉官网商品页注入按钮 | 「乐淘一番-煤炉一键代购插件」上架 Chrome 应用商店：[chromewebstore.google.com/detail/…jbgmmkknidlccpcblbncffmbkajfmmbl](https://chromewebstore.google.com/detail/%E4%B9%90%E6%B7%98%E4%B8%80%E7%95%AA-%E7%85%A4%E7%82%89%E4%B8%80%E9%94%AE%E4%BB%A3%E8%B4%AD%E6%8F%92%E4%BB%B6/jbgmmkknidlccpcblbncffmbkajfmmbl) |

> 三种并存说明一件事：**他们没有把「官方 API」当作唯一出路**。站内搜索要自建索引（成本高、风控敏感），插件/贴链接是低成本长尾兜底。★ 我们的渠道只有微信小程序（无插件），所以「贴链接」是我们唯一能零成本拿到的同款入口。

### 2.2 ★ 商品级三态闸 —— 最值得抄的一个机制

官方指南明确写了每件商品在系统里有购买状态：

| 商品状态 | 触发条件（原文） | 系统行为 |
|---|---|---|
| **不支持购买** | 标题含 `xxx様専用` / `xxxさん専用`（已被别人预定） | 「乐淘一番也会对其进行**屏蔽**」 |
| **人工代买** | 标题/简介含 `コメント必須`、`即購入不可/NG/NO/だめ/ダメ`、`購入前コメント`；或日本国内运费「由买家承担」（到付） | 「需**转人工订单**进行购买」；到付的那种要客服先收运费再「**为您开启购买权限**」 |
| **可直接购买** | 其余 | 秒切自动下单 |

另有 `プロフ必読` / `プロフィール必読` / `説明必読` 一类卖家规则，只做**风险提示**不拦购买。

> ★ 这条是**风控不是体验**：他们 FAQ 自己写了代价 ——「若采用了错误的购买方式而引起卖家反感，将严重影响代购成功率，甚至可能导致**采购账号被卖家拉黑或差评**，以至于今后再也无法购买该卖家所售商品，**影响使用本平台的客户的全体利益**」。
> 也自己承认漏抓会造成误判：「现处于程序公测阶段，平台提供的 **API 对接功能并未完善**，导致可能部分商品并未被设置，需自行判断」。
>
> 对我们的含义：代切不是「搜到 → 下单 → 完」，**下单前必须有一层商品级准入判定**（能不能自动买 / 要不要人工先谈 / 干脆不许买）。这一层一期完全没有，且**它需要人工运营介入**（规则会漂移、卖家会改标题）。

### 2.3 支付 → 秒切 → 失败全退

- 「支付成功后，可观察**秒切状态**，秒切成功即购买成功，购买成功后无法取消订单；反之**秒切失败，则会全额退还**。若后期因为卖家原因无法发货等其他问题而被取消订单，也会**全额退还**…退款会在 1~2 日内原路返回。」（官方指南 FAQ）
- 卖家主动取消 → 订单状态变「卖家已取消」→ 会员在订单详情点退款按钮 → 1~2 日原路退。
- 「代购手续费及留言手续费不予退还」——**服务费不退、商品款全退**。
- 「成功下单的订单，**不可因为自身原因而取消**」。

> 对我们的含义：这套语义一期已有 80% —— `gz_jp_order`（钱）+ `gz_jp_order_item`（行级履约/退款/`purchase_failed` → 行级退款）就是为这个形状建的。**但「买不到就全额退」在代切里是主路径不是异常路径**（一期是店员标失败，代切是常态秒切失败），所以：**订单超时关单缺失 + 退款卡单无自动补偿**这两个已知缺口（`GO-LIVE-CHECKLIST.md`）在代切下会被放到最大。

### 2.4 费用与定价（只取我们能用的那条）

- 基础代购手续费：单件 <7,000 日元收 200 日元；>7,000 日元按 3% 收、上限 1,000 日元。留言服务：议价 100 / 要照片 200 / 换物流 100 日元（公测期全免）。出处：§1 的上线公告。
- **日本国内运费**：卖家包邮（`送料込み(出品者負担)`）则免；否则**买家到仓后另付**。
- **国际运费**：走乐一番转运，EMS/航空/海运/DHL，**买家另付**，可合箱。
- 议价幅度与「商品页面更新时间」联动（5 天内 5% / 5-7 天 10% / 7-10 天 15% / 10 天以上 20%）——说明他们**把商品页更新时间也抓进了自己的模型**。

> ★ 我们的口径与它**根本不同**：甲方已定「代切也包邮」（`doc/16` §附录），一期订单表**没有运费列**（`V202608070632` 设计要点 1）。
> 那么乐淘一番那两条「买家另付」的运费在**我们这边全部变成甲方成本**：① 卖家不包邮（着払い/到付）；② 超大型/超重商品的额外到付（官方指南都专门提醒过这种「标价含运费却收到付」的极个别情况）。
> **这是必须让甲方拍板的一条口径**（见 §4 问题 3），不是技术问题。

### 2.5 运营侧细节（低成本高价值，抄的是文案与规则不是代码）

- 「自动翻译」：站内可开自动翻译用中文搜煤炉（其晒单/攻略原话：「乐一番煤炉代切 可以直接开启[自动翻译]，输入中文搜索哦~」）。谷圈客人只会打中文（「蓝色监狱 吧唧」），煤炉标题是日文（`ブルーロック 缶バッジ`）——**不解决这一步，站内搜索等于没有**。
- 收藏/订阅（「新增了专属的订阅服务，操作指南：1.收藏喜欢的宝…」）→ 对应我们诊断文档里的「许愿/求购入口」。
- 清关话术（官方指南 05 节）：走关税补贴线要求「无二手/中古/煤炉/merucari 等声明」，申报**别写**二手关键词，海关抽查要购物证明时「建议隐去煤炉的 logo 与网址」——★ 这是**灰色地带的自陈**，也是我们给甲方做风险告知时必须引用的原话。

## 3. 「煤炉的 API 拿不到」这件事的真相

| 事实 | 出处 |
|---|---|
| Mercari 有 **Partner API**，但「Partner-only API access…**Not self-serve**; access granted under **partnership agreements**」 | [apis.io — Mercari Partner API](https://apis.io/apis/mercari/partner-api/)（索引自 mercari 官方 business 页 `about.mercari.com/en/business/`） |
| Mercari 在**加强事业者向越境 EC 基盘**（对日事业者合作是官方在推的方向） | [ecnomikata.com/ecnews/cross-borderec/48337](https://ecnomikata.com/ecnews/cross-borderec/48337/) |
| BEENOS（Buyee 系）为「メルカリ ↔ US 版メルカリ」互通提供支持 | [beenos.com 新闻稿](https://www.beenos.com/file/press-release/6555/20240802_bns_pr.pdf) |
| 乐一番**自述**为「Mercari（煤炉）官方合作伙伴」「使用煤炉官网**认证账号**（楽一番*）为用户代购」 | [煤炉站点购物指南](https://letaoyifan.com/article/id/376) |
| 乐一番自陈「平台提供的 **API 对接功能**并未完善」 | 同上 |

> **结论**：路径是「**先拿到事业者/代理购入合作资格 → 才谈得上 API 与认证账号**」，而不是「找到一个可以直接调的接口」。
> 甲方「API 拿不到」的可行解读：① 申请被拒/没申请；② 缺对日法人主体；③ 缺采购账号资质（认证账号要挂日本公司）。**这三条要问清楚是哪一条**，因为它决定我们是走商务还是走灰色技术。

## 5. miniapp-jp 现状：代切能复用多少

### 5.1 现在是什么（一期，2026-08-14 验收，24/24 ticket `done`）

- 前端 `code/main/miniapp-jp`：13 页 / 原生 tabBar 2 格（首页、我的）。页面：`index`、`event`、`product/detail`、`cart`、`order/{confirm,list,detail,result}`、`me/{index,about,profile}`、`login`、`agreement`。API 层 `src/api/gz-jp/{event,product,cart,order,format}.ts`。
- 后端 `ruoyi-modules/ruoyi-gz-jp`：8 个 service（事件/商品/购物车/订单/订单管理/履约/退款/…），mp 端点为 `/app/gz/jp/{event,product,cart,order}`，商品与场**匿名可读**。
- 数据模型（`V202608070632__GZ-JP-105-…sql`）：
  - `gz_jp_order` **只管钱**（created/paid/cancelled/partial_refunded/refunded，无运费列）。
  - `gz_jp_order_item` **是核心**：`fulfill_status` / `carrier_code` / `tracking_no` / `refund_status` / `refund_amount_cent` 全在行上。
  - `gz_jp_order_item.source` 默认 `'batch'`，**专为二期代切预留**（`GzJpItemSource.java` javadoc 原话：「二期只加一个枚举值 `snap` + 一条字典数据，表结构/索引/已有数据一律不动」）。

### 5.2 能直接复用的（代切不用重做）

| 能力 | 落点 |
|---|---|
| 订单/订单行 + 资金链路 | `gz_jp_order` / `gz_jp_order_item`；支付走 `gz-common` 的 pay SPI（`PayBusinessType.JP`），全款 |
| **行级退款**（买不到只退那几款） | `gz_jp_refund` + `JpRefundCallbackHandler` + `GzJpRefundTxService` |
| 履约状态机（可跳态、不可回退、不可跨终态） | `GzJpFulfillStateMachine`；状态：`purchasing → purchase_failed / await_seller_ship → jp_shipped → customs → cn_sorting → delivered` |
| 履约看板（按客人聚合、跨订单、批量推进、填一个顺丰单号） | `GzJpFulfillServiceImpl` / `GzJpFulfillController`（`advance` / `ship` / `mark-failed`）——**代切的人工代买可以直接落在这里，零改造** |
| 购物车 / 下单确认 / 支付 / 订单列表与详情 | mp 13 页里 8 页 |
| 商品图（禁存裸 URL，渲染时换 1h 预签名） | `gz_file_object` + `IGzFileService` → **煤炉商品图的转存落点已经有了** |
| 地址快照 / 用户 / 登录 | `gz-user` 域 |

### 5.3 缺的 / 结构不兼容的（这才是代切的工作量）

1. **商品目录维度完全不同**。`gz_jp_product.event_id` 是 `NOT NULL`，且商品由店员在「场」内上架（`gz_jp_product` 有 `product_no` / `status=on_shelf` / `sort_no`，`accept` 还断言过「无 stock 列、无 SKU」）。代切是 REQ-SNAP-002 原话「**没有上架部分**」——商品来自外部平台、按外部 ID 标识、**没有场**。
   → 要么新表（推荐：外部商品缓存/索引，带 `platform` + `external_id` + 卖家/成色/配送方式/是否已售出），要么给 `gz_jp_product` 开口子（不推荐：会污染一期的「场」语义与唯一键）。
2. **零搜索能力**。`_evidence-现状盘点.md` 已实测：一期「客人侧几乎没有『帮我找到想买的货』的能力（零搜索、零分类、零排序、无分享）」。代切的入口本身就是搜索，**这一步是净新增**。
3. **汇率 + 加点定价**。一期单价是店员手填人民币分（`price_cent`）。甲方口径（REQ-SNAP-007）是「浮动汇率 + 加点、下单锁价」→ 需要汇率源 + 定时抓取 + 加点配置 + **下单那一刻把汇率锁进快照**（快照结构 `JpOrderSnapshot` 要加字段）。
4. **商品级三态闸**（§2.2）：可自助 / 需人工 / 不可买 + 人工开权限。一期没有这个概念。
5. **采集管道 + 反爬 + 图片转存**：新模块 + 新 job，且是**长期运维**（煤炉改版即失效）。
6. **中文搜日文**：要么翻译/词表，要么教用户贴日文关键词（乐淘一番两条都用）。
7. **两个已被点名的既有缺口在代切下会放大**：未支付订单无超时关单（`ruoyi-gz-jp` 无 `@JobExecutor`，`GzJpOrderMapper.markCancelled` 是死代码）；退款卡单无自动补偿（事务提交后、调微信前挂掉 = 永远 `refunding`）。

## 6. 若做代切：三条路径与代价

| | **A. 贴链接代切**（最小可用） | **B. 站内搜索 + 秒切**（= 乐一番形态） | **C. 混合 / 官方合作（§4 解读 A）** |
|---|---|---|---|
| 客人路径 | 复制煤炉链接 → 贴进小程序 → 系统抓这一件 → 确认下单 | 小程序内搜/逛 → 加购 → 结算 | 拿认证账号 + 官方接口，其余同 B |
| 数据侧 | **单次按需抓取**，不需要索引、不需要批量爬 | 批量采集 + 索引 + 图片转存 + 增量刷新 | 官方接口，最稳 |
| 抢单 | 人工（复用现有履约看板 + 采购动作） | 自动「秒切」，失败全退 | 自动，且合规 |
| 新增模块 | 无新表也可先做（订单行 `source=snap` + 快照加外部字段） | 新表 + 新模块（采集/搜索/图片）+ 汇率模块 | 同 B 减去采集 |
| 风险 | 最低（不批量爬、不碰搜索索引） | 高（封号/封 IP/微信审核/清关） | 低（但准入不受我们控制） |
| 成本 | **S–M** | **L–XL** | 代码 L–XL + 甲方行政周期 |
| 建议 | ★ **先做 A 上线，把「买不到全额退 + 人工代买」这条业务闭环跑通**；B 等 A 的真实订单量证明值得再上 | 直接上 B = 把最贵的部分建在最不确定的前提上 | 与 A 并行推进商务，谈成了再决定要不要 B |

> 关键判断：乐淘一番是**平台**（9 站聚合、转运、仓储、付费检品拍照、客服团队），我们是**一家谷子店的拼团工具**。它的站内搜索是它的核心资产（要养采集/反爬/客服/审核），而我们照抄下来的收益是「客人少一次复制粘贴」，代价是每年代码 + 运维 + 封号风险。**这一点建议原话讲给甲方**。

## 7. 硬约束与风险（做之前必须写进方案）

1. **微信侧**：境外平台商品信息聚合 + 图片域名。乐淘一番的图片一律走自有 CDN（`image2.leyifan.cn`），与其微信小程序并存——**有先例**，但仍需海淘类目资质（甲方在办，`doc/16` §二 第 3 项）+ 自有 ICP 备案域名（REQ-SNAP-003 note 已记）。
2. **煤炉侧**：批量采集与自动下单均违反其利用规约；后果是账号拉黑/封禁、IP 限制，且**会伤害采购账号的卖家信誉**（乐淘一番 FAQ 原文承认过）。规避手段只有官方合作，或接受风险 + 多账号轮换 + 监控告警 + 自动降级人工（`doc/16` §附录 已向甲方披露）。
3. **清关/合规**：乐淘一番官方指南自己教用户「隐去煤炉 logo 与网址」「申报别写中古」——这是**灰色地带证据**。合同 §16 已定「跨境物流不自动抓取、甲方后台手动推进」，代切若涉及申报口径，**必须落在甲方责任**，不由我方系统生成规避性文案。
4. **资金**：一期口径是「全款 + 包邮 + 行级退款」，代切继续沿用；若要引入「先报价后付款」（乐淘一番给到付商品开权限那种），**那是新的资金形态，属商业口径变更**（AGENTS.md §3 第 14 条），需甲方书面确认。
5. **不能动的**：`ruoyi-gz-jp` 一期表结构（迁移 append-only）；代切应以**新模块 + 新迁移**落地，`order_item.source` 只加枚举值 `snap` + 字典数据（这正是 ADR-0020 §4 与 `GzJpItemSource` javadoc 预留的用法）。
