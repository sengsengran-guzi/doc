# ADR-0008 拼豆座位由「具体座位 A1-A10」改为「座位类型配额模型」（单笔单时段，按 booking 计数）

- 日期：2026-06-09
- 状态：Accepted
- 决策人：Kevin（甲方 V1.2 调整需求，kevin-product 评估，kevin-coder 落地）
- 关联 ticket：GZ-BEAN-013（类型配额 config + admin 配数量/单价 + 废弃具体座位）；下游 GZ-BEAN-014/015（ADR-0007 付费状态机依赖本模型）
- 落地批次：D12（BEAN-013 admin 地基）

---

## Context

V1.0 拼豆预约采用**具体座位模型**：成都门店预先画好编号座位 A1-A10（`gz_bean_seat` 表，一行一个具体座位），用户预约时**选定某个具体座位**，admin 端要「画座位图 / 维护每个座位」。

甲方在 V1.2 调整批次提出：**去掉具体座位**。理由（甲方运营视角）：

- 拼豆店实际是「按桌型分区」运营（单人位 / 双人桌 / 四人桌），不存在「A3 和 A4 有什么区别」——用户根本不在乎坐哪张具体桌，只在乎「有没有四人桌位」。
- 维护 A1-A10 座位图对甲方是无谓负担；扩容/调整桌位要改座位图，繁琐。
- 真实诉求是**库存配额**：每种座位类型有几个、约满即拒，而非精确到座位号的分配。

于是要把模型从「具体座位分配」推倒为「座位类型配额」。叠加 V1.2 的拼豆付费（ADR-0007），座位类型还要带**单价**。预约粒度甲方明确为**单笔单时段**（一笔预约 = 1 座位类型 + 1 时段，多类型 / 多时段用多次预约表达，**不引子表**）。

设计取舍问题：**改现有 `gz_bean_booking` 表（原地补 seat_type + 付费列），还是全新一套表？**

## Decision

### 1. 废弃 `gz_bean_seat` 用于预约（表保留不 DROP，停用）

- `gz_bean_seat`（A1-A10 具体座位）**不再用于预约**，逻辑停用。
- **物理保留、不 DROP**（强约束 #5 风格：destructive 操作避免；保留 V1.0 历史数据可追溯 + 旧 booking 迁移期还要读它做 seat→seat_type 映射）。
- 后续所有「座位」语义走类型配额，**禁止**新代码再 INSERT/依赖 `gz_bean_seat` 做预约分配（§0 自检 / QA 打回项）。

### 2. 新建座位类型配额配置表 `gz_bean_seat_type_config`

每门店 × 每座位类型一行配置（DDL 走 Flyway，强约束 #2/#3）：

| 列 | 说明 |
|---|---|
| `store_id` | 门店（V1.0 仅成都一店，强约束 #13；多店配置代码留接口 UI 隐藏） |
| `seat_type` | 座位类型，走**字典 `gz_bean_seat_type`**（`single` 单人 / `double` 双人 / `quad` 四人桌；可扩展） |
| `quantity` | 该类型在该门店的**数量**（= 配额上限） |
| `price_cent` | 该类型**单价**（分，供 ADR-0007 计费用） |
| `enabled` | 是否启用 |
| — | `UNIQUE(tenant_id, store_id, seat_type)`（强约束 #3 唯一约束必含 tenant_id） |

admin 端形态从「画座位图 A1-A10」**简化为「配每类型数量 + 单价」**（一个门店几行配置即可，GZ-BEAN-013）。

### 3. 预约改引座位类型（不再引 seat_id，单笔单时段，无子表）

- `gz_bean_booking` 主表原地补 **`seat_type`** + `seat_type_snapshot`（下单时类型名快照）+ `sess_date` / `slot_start` / `slot_end`（单时段直接挂主表）+ `amount_cent`（该类型单价快照），**不再有 `seat_id`，也无计费单元子表**。一笔预约 = 一行 booking（1 类型 1 时段）。
- 可用量计算 = `gz_bean_seat_type_config.quantity` − 该 `(store, seat_type, date, slot)` 组合下的**活跃 booking 计数**（活跃口径见 ADR-0007 §2：booking `pay_status IN (unpaid,paid,verified)`）。
- mp 选座**实时显示余量**：每个 (类型,日期,时段) 返回 `余量 = quantity − 活跃 booking 数` → 「还剩 N 个单人座」（N>0）/「已满」灰显（N≤0）。
- 约满即拒：活跃 booking 计数达到 `quantity` → 该类型该时段不可再约（防超卖事务计数见 ADR-0007 §2，本 ADR 只定数据模型，并发口径在 0007）。

### 4. 取舍记录：选「改现有 booking 表」而非「全新表」

**选定**：废弃旧 `gz_bean_seat`（保留不删）+ 新建 `gz_bean_seat_type_config` 配置表 + `gz_bean_booking` 主表 ALTER（补 seat_type + 单时段 + 付费列，ADR-0007）。**无子表**（单笔单时段，一行 booking 自洽）。

**被否方案：全新一套 booking 表**（`gz_bean_booking_v2` + 全新配置表，旧表整体弃用）。

| 维度 | 改现有表（选定） | 全新表（否决） |
|---|---|---|
| V1.0 数据兼容 | ✅ 旧 booking ALTER 后原地迁移（ADR-0007 §3），主键/外键/审计连续 | ❌ 要写双表迁移搬数据，admin/mp 查询要兼容两套 |
| admin/mp 改动面 | 中（座位选择 UI 换、列表加字段） | 大（整条链路指向新表） |
| 历史核销/查询 | ✅ 原表原地，不断 | ⚠️ 跨新旧表聚合，对账复杂 |
| 后续维护 | ✅ 单一 booking 真源 | ❌ 长期双表并存或二次合并 |

改现有表在「兼容 V1.0 数据 + 改动面可控 + 单一真源」上全面占优；旧 V1.0 免费单本就单类型单时段，与 V1.2 模型同构，**原地 ALTER 即可，无需子表也无需新表**。全新表只在「想彻底切割旧模型」时才有意义，但 V1.0 数据要留，切割得不偿失。

### 5. 旧数据迁移（与 ADR-0007 §3 同一迁移）

旧 `gz_bean_booking`（具体座位、单时段）与新模型同构，**原地 ALTER 迁移、无子表**：每条旧单补 `seat_type`（按旧 `seat_id` → `gz_bean_seat.seat_type`（若旧表有类型字段）或统一置默认 `single`）+ `seat_type_snapshot` + `amount_cent=0`（历史免费单）。详见 ADR-0007 §3（迁移在 GZ-BEAN-014 内一并做）。

## Rationale

- **贴合甲方真实运营**：拼豆店本就按桌型运营，配额模型 = 甲方脑子里的真实模型；具体座位 A1-A10 是过度建模，维护成本高、用户无感。
- **配额比座位分配更省心**：admin 从「画图维护 10 个座位」降为「配 3 行类型数量」；扩容只改数字，不改座位图。
- **保留旧表不 DROP**：守 destructive 操作红线 + 留 V1.0 数据可追溯 + 迁移期要读它做映射；代价仅一张停用表占库，可接受。
- **改现有表胜全新表**：兼容 V1.0 数据 + 单一 booking 真源 + 单笔单时段无需子表，长期维护最优（取舍表见 §4）。
- **字典化座位类型**：`gz_bean_seat_type` 字典让类型可扩展（未来加「包厢 / VIP 桌」只加字典项 + 一行 config），不写死枚举。

## Consequences

- ✅ admin 座位配置从「画座位图 A1-A10」简化为「配每类型数量 + 单价」（GZ-BEAN-013），甲方运营负担大降。
- ✅ 预约模型变为库存配额（类型 × 时段约满即拒，按活跃 booking 计数），契合甲方真实诉求，并为 ADR-0007 付费计费（单笔金额 = 该类型单价）提供数据基础。
- ✅ V1.0 booking 数据原地迁移、不断档，历史核销/查询不受影响。
- ✅ 单一 booking 真源（无新旧双表），对账/审计简单。
- ⚠️ **`gz_bean_seat` 成停用表**：保留不删，但禁止新代码用于预约（§0/QA 打回项）；其相关 admin「座位图」入口在 GZ-BEAN-013 下线/隐藏。
- ⚠️ **mp 预约 UI 重构**（GZ-BEAN-015）：从「选具体座位」改为「选座位类型（显实时余量）+ 选时段」，单笔金额 = 该类型单价（ADR-0007）；多类型 / 多时段用多次预约表达。
- ⚠️ **字典需 seed**：`gz_bean_seat_type`（single/double/quad）字典项随 GZ-BEAN-013 Flyway seed（强约束 #5；菜单复用 6000 GZ-BEAN 段）。
- ⚠️ **并发/防超卖口径不在本 ADR**：本 ADR 只定数据模型（配置表 + booking 主表补列 + 可用量公式 = quantity − 活跃 booking 数）；下单事务防超卖的悲观计数口径在 **ADR-0007 §2**，两份配套阅读。
