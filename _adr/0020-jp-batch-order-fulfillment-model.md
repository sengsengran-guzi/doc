# ADR-0020 日本拼团履约模型：状态挂商品行 · 不建包裹表 · 行级部分退款

## 背景

一个「场」上架几十款商品，客人一单能买 30 款。每款货源不同（线下现货 / 官方预订 / 代抢），到货时间天差地别，有的根本抢不到。甲方四条原话把建模粒度定死了：

| 需求点 | 甲方原话 |
|---|---|
| REQ-FULFILL-003 | 每一款商品都显示状态 |
| REQ-FULFILL-004 | 一个客人比如买了 30 款商品 我们发货了 20 款 那么 20 款都显示顺丰单号 xxxx 后台员工去填写 |
| REQ-FULFILL-005 | 客人付了钱没抢到货 怎么办 —— 原路退回客人微信 |
| REQ-FULFILL-006 | 这个跟客人无关 多少包裹 单个还是多个 客人不能决定 |

这四条互相咬合：状态粒度决定退款粒度，也决定包裹要不要显式建模。三个决策拆开写会互相引用，故合一份 ADR。

---

## 决策

### §1 履约状态挂 `gz_jp_order_item`，不挂 `gz_jp_order`

**为什么这么定**：一单 30 款各自的进度天然不同 —— 现货那款今天就到日本仓，官方预订那款要等三个月，代抢那款可能明天就判定失败。订单级只有一个状态字段，30 款走在 7 个不同状态上，订单级表达不了；退而求其次取"最慢的那款"，客人打开订单永远看到同一个进度条，与「每一款商品都显示状态」正面冲突。

**分工**：`gz_jp_order` **只管钱**（`total_amount_cent` / `pay_transaction_id` / `business_status`），`gz_jp_order_item` **管货**（`fulfill_status` 七态 + `carrier_code` / `tracking_no` / `shipped_at` / `refund_status` / `refund_amount_cent`）。订单级 `business_status` 是行状态的 rollup 结果、不是独立真源；支付态与履约态互不覆盖，沿用 ADR-0007 的双状态机正交范式。

**代价**：

1. **所有履约查询下沉到行表**。行数 = 订单数 × 款数（一单 30 款是常态，不是极端值），admin 履约看板与 mp 订单详情都必须按 item 分页，不能按 order 分页。主视图靠 `idx_user_fulfill (tenant_id, user_id, fulfill_status)` 兜住；`user_id` 在行上冗余一份也是为此（按客人聚合且跨订单，每次 join 订单表不划算）。
2. **订单级状态不能直接写**。任何行状态变更都要重算 rollup，写路径多一步；批量推进时 rollup 有竞态，靠 `gz_jp_order.version` 乐观锁 + 把 rollup 限制在退款回调这条串行链路上算。
3. **前端不能用常规订单页布局**。「一个订单一个状态标签」在这里是错的，订单详情必须是一张按行展开的进度列表。

**什么情况下要推翻**：只有甲方改口「整单一起发、整单一个状态」才成立 —— 那等于放弃集单代购的形态，实际不会发生。真正需要留意的是反向压力：若将来要「一款商品拆多次部分发货」（买 3 个先发 2 个），推翻的不是本决策，而是要在行下面再加一层。届时优先做法是**下单时就把 qty 拆成多行**，不要在行上再挂子表 —— 加第三层会把 rollup 变成两级，是本 ADR §2 已经否掉过的复杂度形态。

### §2 不建包裹表 —— `tracking_no` 本身就是包裹标识

**为什么这么定**：甲方的实际操作动作是「在履约看板按客人筛出到齐的货 → 勾一批 → 填一个顺丰单号 → 这批行一起置发货完毕」。这个动作里**没有「创建包裹」这一步**，包裹是填单号这个动作的副产品。同一个 `tracking_no` 的行集合 = 一个包裹，这是天然成立的等价关系，不需要一张表来维持它。

再对上 REQ-FULFILL-006：客人侧完全不感知包裹（mp 只显示每款货各自的状态 + 单号），后台主视图是**按客人聚合**（且允许跨订单合并同一客人的货），也不是按包裹聚合。**两端都没有以包裹为主语的视图** —— 这才是不建表的依据。不是"省一张表"，是没有任何一个场景需要包裹这个实体拥有自己的身份、生命周期和属性。

**代价**（`GROUP BY tracking_no` 能顶掉的那部分不算代价，真正的代价是这四条）：

1. **包裹没有自己的属性位**。要记包裹重量、运费成本、打包人、发出仓库，无处可挂 —— 只能冗余到每一行，或者到那时才建表。
2. **包裹没有自己的状态机**。「这个包裹整体退回 / 丢件作废」这类以包裹为单位的原子动作做不了，只能逐行改。
3. **单号手工填，填错就串包**。两个不同包裹填了同一个单号，在模型里就是同一个包裹，无从分辨。只能靠 admin 侧输入校验 + 二次确认缓解，**不能靠数据库约束** —— 同一单号出现在多行本来就是合法的，正是设计意图。
4. **"包裹"只对 delivered 行成立**。`tracking_no IS NULL` 的行天然不属于任何包裹（还没发货，这是对的），但任何按包裹的统计都得先过滤非空，写查询时容易漏。

聚合查询靠 `idx_tracking (tenant_id, tracking_no)` 保证不退化成全表扫。

**演进记录**：第一版设计是三层 —— 订单 / 商品行 / 包裹，包裹表持有单号、快递公司、发货时间，商品行外键指向包裹。甲方 2026-08-05 对「多少包裹、单个还是多个，客人不能决定」的答复暴露了包裹在业务上是**隐式**的：它没有客人侧界面，也没有后台的独立管理入口，只是员工填单号的结果。第三层退掉，包裹字段（`carrier_code` / `tracking_no` / `shipped_at`）平铺进商品行。

**什么情况下要推翻**（任一成立就建包裹表）：

- 接快递 API（下单取号 / 自动同步物流轨迹）—— 包裹要有自己的生命周期和回调落点；
- 甲方要按包裹核算运费成本或打包绩效 —— 包裹需要自己的属性位；
- 出现「包裹整体退回」这类以包裹为单位的业务动作。

迁移成本可控：建表后按 `GROUP BY (tenant_id, tracking_no)` 回填即可，历史数据一条不丢 —— 这是敢先不建的底气。

### §3 退款是行级的部分退款，订单级 rollup

**为什么这么定**：状态粒度是行，退款粒度必须跟着是行。30 款里 2 款没抢到，只退这 2 款的 `amount_cent`，其余 28 款照常发货。退的是「原支付单的一部分」，所以走微信**部分退款**。行上写 `refund_status` / `refund_amount_cent`，订单级由剩余行 rollup：有失败行但非全部 → `partial_refunded`；全部行失败 → `refunded`。

**★ 实施前硬查项已执行，结论：现有 `PayRefundController` 不支持指定金额，行级退款无法直接复用现有 GZ-PAY 退款入口**（这是本 ADR 与原始 ticket 描述最大的出入 —— 它不是"待查"，是"已查出不支持"）。四道闸如下：

| 层 | 现状 | 结论 |
|---|---|---|
| `IWechatPayClient.refund(RefundRequest)` | record 已含 `refundAmountCent` + `totalAmountCent` **两个独立参数** | 通道层**天然支持**部分退款，不用改 |
| `RefundApplyBo` | **无 amountCent 入参**，javadoc 明写「仅全额退款…杜绝前端传错金额（决策 D2）」 | 须加金额入参，或另开 jp 专用入口 |
| `PayRefundServiceImpl.apply` | 两个金额位都传 `refund.getRefundAmountCent()`，注释「全额：原单总额 = 退款额」 | 须拆开：total 取原交易 `amount_cent`，refund 取行金额 |
| `PayRefundTxService.createRefunding` | `countActiveByTransactionId(...) > 0` 即抛「该订单已有进行中或已完成的退款，不可重复退款」 | ★ **最硬的一处**：一笔支付只允许一条退款单。同一单退第 2 款时直接被拒 |
| `gz_pay_transaction` 状态机 | `paid → refunding → refunded`，退款回调把整笔 txn 标 `refunded` | `refunded` 是终态，部分退一次就锁死剩余部分；须区分「部分已退」与「全退」 |

**所以行级退款不是「调个现成接口」，是支付域的实质工作。** 摆在面前的是两条路：
① 改造共用的 GZ-PAY，把退款能力从「一单一次全额」扩成「一单多次部分」；
② 给 jp 域开独立退款入口，只共用 `IWechatPayClient` 通道层。

**决策：走 ②（Kevin 2026-08-06 拍板）。**

新建 jp 专用退款 Service + 退款单表，直接调 `IWechatPayClient.refund`（通道层本就支持指定金额），**拼豆 / 回收的资金链路一行不动**。

选 ② 而不是 ① 的理由：①要放宽 `createRefunding` 的重复退款闸门，而那道闸门正在保护拼豆与回收的线上资金安全；放宽它就必须同步补「已退总额 + 本次 ≤ 原单总额」的金额校验，并对两条既有业务线做全量资金回归。**为了一个新业务去动两条在跑的资金链路，风险收益不成比例。**

**代价**（走 ② 之后仍然要付的）：

1. **退款逻辑两套**。jp 一套、拼豆/回收一套，同类问题要修两处。将来若第三条业务线也需要部分退款，
   应把 jp 这套提取成通用能力，而不是再复制第三份。
2. **退款回调按行回落**。jp 侧的退款回调不能假设「回调到 = 整单退完」，必须按 `out_refund_no`
   回到具体 order_item 行，再重算订单 rollup。
3. **对账口径按行扣减**。同一订单会既贡献 GMV 又贡献退款，对账中心不能再按单粒度冲抵，
   且要兼容 jp 与既有两个退款来源。

> 走 ① 才会付的那条代价 —— 放宽 `createRefunding` 的重复退款闸门、补金额校验、对拼豆/回收做全量资金回归
> —— **正是选 ② 要规避的**，不在上面这张单子里。

**什么情况下要推翻**：① 甲方改口「没抢到就整单退」—— 不成立，为 2 款失败退掉另外 28 款已买到的货客人和店家都不接受；② 拼豆或回收自己也需要部分退款了 —— 那时两套合一，把 jp 这套上提为共用能力，届时才值得动 `createRefunding` 那道闸门。

### §4 `order_item.source` 预留来源维度，二期加值不改表

**为什么这么定**：甲方明确「后面的部分用同一个系统」（REQ-SNAP-004）—— 二期代切的订单要汇入
同一套订单与履约链路。行表加一列 `source`（一期恒为 `'batch'`，二期加 `'snap'`），
让两种来源在同一张表里共存，二期只加枚举值、不动表结构。

**代价**：一期这列是常量，所有查询都带一个恒真条件，读起来像冗余。查询与索引要预先按
「带 source 过滤」设计，否则二期数据进来时既有查询会静默混入代切订单。

**什么情况下要推翻**：如果二期最终判定代切的履约链路与拼团差异过大（例如代切需要自己的状态机），
那时应拆表而不是继续共用 —— 届时 `source` 列退化为历史包袱，可随拆表一并去掉。

## 附带口径：「购买失败」不是异常路径

`purchase_failed` 不是错误处理，是**常走的路** —— 别人先买走 / 卖家取消订单 / 商品下架，在代购业务里天天发生。它的健壮性要求等同主链路：

- 它是 `fulfill_status` 的**分支终态**（与 `delivered` 并列），不是挂在某个状态上的失败标记；进了这个态就不再往履约链下游走。
- 下游（行级退款 → 回调 → rollup）要有和发货链同等的幂等、重试与人工兜底，不能写成"异常分支 catch 一下记个日志"。
- admin 必须支持**批量**标记购买失败 —— 一场货被抢光是批量事件，不是零星单个。
- 客人侧要有明确文案：哪款没抢到、退了多少、退到哪里。不能只给一个红色 error 态。

对应地，不要给它写「非预期错误 → 告警」这类处理：它是预期内的。
