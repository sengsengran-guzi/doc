# ADR-0022 回收预约按 1 小时格占用（点数档驱动连占 N 格）

- **状态**：已决（已实施 D22 / GZ-RECYCLE-012）
- **日期**：2026-08-26
- **关联**：**完全取代** GZ-RECYCLE-007（命名时段档 + 每档 1 单 + `occupy_next_slot` 溢出 + FLAT 末档规则，该决策只靠迁移注释承载、无 ADR）／ **修订** ADR-0021 §1 §2 §3 ／ **不取代** ADR-0012 ／ **实现蓝本** ADR-0011（拼豆 1h 区间预约）／ doc/10 §13 ／ doc/11 §12

## 背景

甲方 2026-08-26 微信原话：

> 「这部分 店员还是要求改成 小时制度 说上午下午这个不行 一天上不了多少人」
> 「小时制度 然后200点的人 自动占满4小时这样」
> 「和拼豆一样 一小时一个格这样」
> Kevin：「如果200点以上，就自动填充上午或者下午？，如果上午有预定，200点以上应该无法预定上午吧」→ 甲方：「对的 但是如果用户选择9：00 点数是100的话 10：00自动被划进去」「200点就四个小时」
> Kevin：「也就是说每50点一小时这样？」→ 甲方：「嗯」

改造前的模型（GZ-RECYCLE-007）：占用单位是 admin 配的**命名时段档**（上午 10-13 / 下午 15-18 / 晚上 19-22），每档恒 1 单，最高点数档靠 `occupy_next_slot=1` 额外占**下一个 enabled 档**（末档无下一档则不占，即所谓 FLAT 规则）。**日容量 = 3 单**，这正是店员抱怨的根源。

一个关键发现让改造成本远低于预期：点数档 seed 的注释原文就是「每 50 点约 1 小时（可后台改）」，`duration_minutes` = 60 / 120 / 180 / 240 / 300 —— **甲方口径本来就在数据里**，只是这一列此前仅用于展示「预计回收时长」，不参与占用计算。

## 决策 §1：占用真源 = `[slot_start, slot_end)` 小时区间

一行 `gz_recycle_appointment` 承载一个左闭右开的整点区间：

```
slot_end = slot_start + N 小时
N = CEIL(gz_recycle_qty_range.duration_minutes / 60)
```

用户只选**起始整点**，系统自动连占 N 格；放不下就不能选。这与拼豆 ADR-0011 §2「一行 booking 存连续区间」完全同构。

**三列的取舍**：

| 列 | 处置 | 理由 |
|---|---|---|
| `slot_start` / `slot_end` | 从「快照展示」升格为**占用真源** | 区间模型对历史数据天然鲁棒：老单 `10:00-13:00` 被解释成占 3 格，只会**多占不会少占** |
| `time_slot_id` | 退休保留（新单写 NULL，占用查询不再读） | 老单「当初选了哪个档」的唯一痕迹，留作审计；删列要连带改 entity/VO/plus-ui，负债大于收益 |
| `spill_time_slot_id` | 退休 + 存量折叠进 `slot_end` 后**物理置 NULL** | 区间模型表达不了「跳过 gap 再占一格」；留着非空值不读 = 给下一个人埋雷 |
| `qty_range.occupy_next_slot` | 退休保留（恒 0，admin 表单**删掉**不是隐藏） | 留一个拨了不生效的开关，店主一定会去动然后困惑 |
| `qty_range.duration_minutes` | 从「仅展示」升格为**占用驱动** | 现有 5 行天然是 60 的倍数，零数据迁移 |

**存量 `slot_end` 不重算**：老单是「档结束」（如上午单 10:00-13:00），方向只能是过占。**绝不能缩短** —— 缩短 = 那格立即对外放开 = 与顾客实际到店时长物理双占（超卖）。交付说明须写明：存量单按原档整块占用，需要释放请用改期或看板「取消」（GZ-RECYCLE-014）。

## 决策 §2：`gz_recycle_time_slot` 语义转向「整点营业窗口」+ 按星期可配

一行 = 一个营业窗口，系统按 1 小时切格（镜像拼豆 `gz_bean_time_slot_template` 的同款语义转向）。**残格不生成**（配 10:00-13:30 只切出 10/11/12），跨窗口 gap（午休）不可桥接。

**必须 reseed 成连续窗口 —— 这是本次改造的硬前置**：现状 3 段最长 3 小时，改小时格后 `pts-150-200`（4h）和 `pts-200-plus`（5h）**在任何一段里都放不下**，会 100% 报 4123，等于把甲方最想接的大单全部堵死，比改造前还糟。

取 `10:00-22:00`（12 格）的理由：与 `gz_bean_store.business_hours` 种子一致；原来的 13-15 / 18-19 断档是「命名档」这种建模方式的产物（三个"档"之间要留缓冲），不是真实闭店 —— 回收是柜台作业，店员全天在岗；5 小时大单放得下。甲方若要午休，admin 自己拆两行即可，切格算法天然处理，**零代码改动**。

同步给营业窗口加**整点 + 至少 1 小时**的服务端校验：非整点会静默丢掉残格，admin 以为开了、顾客约不到、店员对不上账。

**GZ-RECYCLE-015 补充（Kevin 2026-08-26「回收的时间应该可以自行配置，参考拼豆」）**：窗口补齐拼豆的三个维度 —— `weekdays`（ISO 1-7 逗号分隔）+ `effective_date` / `expire_date`。此前回收只有「门店 + 起止 + 启停」，**配不出「周末与平时营业时间不同」**，而甲方本来就说过「周末会开四个四人桌」「平时要看具体情况」。

取窗口从 `listEnabledByStore(storeId)` 全面改为 `listEnabledForDate(storeId, date)`（逐字镜像拼豆 `selectEnabledSlotsForDate`）—— **切格算法本身一行没动**，只是取窗口时多一层按日期过滤。周看板行头相应改为**七天并集**（周末与平时窗口不同，只取某一天会让另几天的格没有行）。

连带 **DROP `uk_tenant_store_time`**：加了 `weekdays` 后 `(store, start, end)` 唯一是错的（「周一至周五 10-22」+「周六周日 10-22」是两行合法配置）。判重下沉 service，口径改为「起止 + 星期完全相同」；窗口重叠不拦（与拼豆同口径 —— 切格 `TreeSet` 去重天然安全，拦重叠反而挡住合法分段）。GZ-RECYCLE-012 为绕开该唯一键加的「软删复活」分支随之退休。

> ⚠️ **切格禁止用 `LocalTime.plusHours` 做循环条件**（GZ-RECYCLE-015 真库端到端逮到，坑位 6）。

## 决策 §3：防超卖 = 逐格升序 `FOR UPDATE` + 区间重叠

逐字镜像拼豆 `countActiveCoveringSlotForUpdate`：

```sql
WHERE tenant_id=? AND store_id=? AND appt_date=?
  AND slot_start < ADDTIME(#{slot},'01:00:00') AND slot_end > #{slot}
  AND status IN (...活跃六态...) AND del_flag='0'
FOR UPDATE
```

**「覆盖格 gi」= 区间与 `[gi, gi+1h)` 重叠，不是 `slot_start` 相等** —— 一张 10:00-14:00 的单确实占了 12:00 这格。回收没有拼豆的「提前放座」概念，止界直接用 `slot_end`。

三条不可动摇的实现约束：

1. **逐格 `cells.contains()` 判连占**，不能只判 `slotStart + N ≤ 窗口尾` —— 后者会让 12:00 起 3h 的单跨过 13-14 午休 gap，把店员的休息时间排上单。
2. **按格升序加锁** —— 交叠区间的加锁顺序一致才无死锁。`manualHold` 的多格入参必须先 `distinct().sorted()`（前端多选顺序不可信）。
3. **Redis `(store, date)` 锁保留** —— 正确性根基是 `FOR UPDATE` + `REPEATABLE_READ` 间隙锁，Redis 只是快速失败优化。回收每格容量恒 1、冲突即失败，先挡在事务外能避免大量间隙锁等待；且 `manualHold` / `reschedule` 已建立在这把锁上，删它是纯洁癖、收益零风险非零。

错误码：4122 `SLOT_TAKEN`（起始格被占）／ 4123 **`SLOT_SPAN_BLOCKED`**（连占放不下；**码号 4123 不变**，mp 已有分支按码走，只改语义与文案，动态带上「需要几小时」）／ 4124 `SLOT_INVALID`（非整点 / 不在营业时间内）／ **新增 4131 `SLOT_PAST`**。

4131 的必要性：命名档时代一天 3 个档，选错概率低；改成 12 格后「选今天已过的时间」是**高频**误操作，不拦就会产出一张必然 no_show 的脏单还白占 N 格 —— 而 prod SnailJob 没部署、no_show cron 根本不跑。手动占用 / 改期豁免（店员回填台账是正常动线）。

## 决策 §4：占格面在提交那一刻冻结，改期绝不活查点数档表

延续 D21 F1 对抗性测试确立的铁律，只是把冻结对象从布尔 `occupyNextSlot` 升级为整数 `spanHours`，写进 `product_snapshot_json`。

**活查是超卖入口**：禁用某个点数档 / 改它的时长都是正常运营动作，一旦改期时活查（`getEnabledByCode` 对禁用档返 null），既有大单的后续小时会被静默放开 → 与顾客实际到店时长物理双占。

改期时的回退链（口径不确定时**一律偏向不放开格**）：

- `source=manual` → 当前区间宽度（新手动行恒 1；存量整档行保持它原本挡住的宽度）
- `source=mp` → ① 快照 `spanHours` → ② `matched_duration_minutes`（提交时冻结列，老单最可信）→ ③ 当前区间宽度

②这一层比改造前更强：旧实现只能拿到布尔（1 格还是 2 格），新实现能从冻结列精确还原小时数。`matched_duration_minutes` 因此从纯展示列升格为**占用宽度的冻结备份** —— 任何「顺手用它做统计 / 回填」的改动都会改变既有单的占用宽度。

## 决策 §5：周看板改「rowspan 区间块」

行 = 营业窗口切出的小时格 **∪ 本周活跃单覆盖到但不在窗口内的孤儿格**。

并集不是可选项：存量整档单、或 admin 事后改窄了营业窗口，都会留下「实际挡着下单但不在窗口里」的格。不做并集 → 店员看到空白却约不上，是最难排查的一类投诉。孤儿行打 `outOfWindow` 标。

cells 改为**一单一个区间块**（不是逐格发 N 个），前端按 `spanHours` 做 rowspan 合并渲染 —— 逐格发会把一笔 4 小时单画成 4 个格，等于把旧模型的 spill 噪音放大 4 倍。`kind='spill'` 随 `spill_time_slot_id` 一起退休：多格占用现在由块自身的区间表达。

行数从 3 变成 ~12，配套：行头只显起点、窗口边界行加粗分隔、行内按钮收进 popover、空闲格加 shift+click 同列区间选、新增图例。`--row-h: 34px` 下 12 行总高 ~350px，**比改造前 3×74px 还紧凑**。

## 拒绝的替代方案：门店级可配的每格容量

**不做，容量硬编码 `SLOT_CAPACITY = 1`。**

1. 甲方从没要过 >1 —— 抱怨是「一天上不了多少人」，而 3 档 → 12 格已经把日容量**翻了 4 倍**，问题已解；
2. 放 `gz_bean_store` 上是错的 —— 那是回收与拼豆**共用**的门店主数据表，塞一个回收专属概念会污染拼豆（拼豆有自己的 `seat_type_config.quantity` 容量模型）；真要配，正确的家是 `gz_recycle_time_slot.capacity`；
3. 容量 >1 会连锁破坏三处语义：周看板「一格一单」的 cell 模型要变成列表、手动占用「占住这格」变成「占住 N 分之一」、`releaseHold` / 改期的格归属判定全部要重写 —— 一整个 ticket 的成本，换一个没人要的能力；
4. 后路已留：容量判定收在 `if (active >= SLOT_CAPACITY)` 一个表达式里，将来加列只需把常量换成 `slotCapacityOf(storeId, cell)`。

## 对 ADR-0021 的修订

| ADR-0021 段 | 关系 |
|---|---|
| §1 手动占用 | **修订输入契约**：`timeSlotIds[]` → `slotStarts[]`；「要占两格就选两格建两行」的原则**保留并强化**（小时格下更自然）；单表 + `source` + `manual_hold` 状态的核心决策**完全保留** |
| §2 改期 | **保留三条硬约束**（排除自身 / 只锁目标 date / 原地 UPDATE 保核销码有效）；**修订约束 2**：「spill 按新档重算」→「span 按冻结 `spanHours` 重算」，禁止活查点数档表的铁律不变 |
| §3 周看板 | **修订列定义**：`enabled 时段档` → `1 小时格`；`kind='spill'` 退休，改 `spanHours` + rowspan；**新增孤儿列并集要求** |

## 坑位

1. **`ACTIVE_HOLD_STATUSES` 从 2 份物理拷贝变 3 份**（Java 常量 + 两个新 `@Select`）。漏改的后果不对称：读路径少一态 = mp 显示可约但提交被拒（可容忍）；**写路径少一态 = 漏拦 = 真超卖**（不可容忍，且只在特定状态的单存在时才复现）。人工 review 挡不住，靠 `GzRecycleActiveStatusConsistencyTest` 反射机械守卫。
2. ~~**`uk_tenant_store_time` 不含 `del_flag`**（软删行仍占唯一键 → 「删掉再新建同样的窗口」吃 DB 1062）~~ —— **已随 GZ-RECYCLE-015 DROP 该唯一键而消失**（加 `weekdays` 后按窗口唯一本就是错的，见 §2）。当初为绕开它加的「软删复活」分支同步退休。留此条是为了让后人知道那个分支为什么曾经存在、又为什么没了。
3. **老包过渡 shim**：小程序发布后用户端有缓存版本，老包只发 `timeSlotId`。service 把它映射成该营业窗口的 `start_time`。**发布后至少保留两周**再连同 BO 字段一起删。
4. **爽约单会锁死当天多个小时格**：一张 5h 大单爽约 = 当天 5 格全废，而 prod SnailJob 根本没部署（25 个 `@JobExecutor` 一个都没跑）。GZ-RECYCLE-014 补的「看板取消顾客单」是**不依赖 cron 的手动兜底**，必须与本 ADR 同批上线。
5. **一人一单守卫（4127）不动** —— 甲方想「一天上更多人」但这是两件事，`USER_ACTIVE_STATUSES` 刻意不含 `paid`/`manual_hold`，改它会连锁影响 `/active` 预检。
6. **`LocalTime` 是环形的，切格不能用它做循环条件**：`23:00 + 1h = 00:00` 且 `00:00.isAfter(23:00)` 为 `false` → `end=23:00` 的窗口会多吐一个窗口外的 `23:00` 格（真库端到端逮到：09:00-23:00 出 15 格而非 14 格）。把防护写在 `add` 之后只挡住死循环、挡不住脏格。正解是按「距零点分钟数」整数循环。**拼豆 `sliceWindowsToHourSlots` 有同一形态的写法**，因其现有窗口都止于 22:00 而未暴露 —— 已记入本 ADR，等有人给拼豆配 23:00 收档的窗口时会复现。
7. **可用性读路径无锁**，与 submit 的 `FOR UPDATE` 之间有天然竞态窗口（UI 显示可约 → 提交拿 4122）。这是**有意设计** —— 展示路径不该为了消除竞态去加锁。
