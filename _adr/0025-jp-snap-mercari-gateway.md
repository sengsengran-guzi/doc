# ADR-0025 代切（煤炉）架构：ruoyi 管钱 · 日本服务只对接煤炉 · 结果不明先对账

**决策者**：Kevin（2026-10-01 ~ 10-03 方案讨论 + /xuqiu「最终想法」点头）
**关联**：REQ-SNAP-005 / 006 / 017 / 026 / 029 / 030 / 039 / 056 · `FLOW:F-JP-05`~`F-JP-09` · `OWN:` 全部 ·
ADR-0020（本 ADR 收窄其 §4「二期只加一个枚举值」的说法，见 §5）· 方案全文 `doc/jp/18-代切二期方案.md`

## 背景

甲方要在拼团小程序里做煤炉代切：用户搜煤炉实时在售商品、付款，系统立刻在煤炉上买下来，买不到就退款。
煤炉官方合作（A1）与接入已有官方合作代购商（A2）都已确认走不通，只能自建直连。直连意味着两件事：

1. 必须有一个跑在日本的进程替我们访问煤炉（下单要与账号常用环境一致的日本 IP）；
2. 没有 API 契约兜底，「下单到底成没成」会出现**不确定**的情况（超时、验证码、断网）。

第 2 点决定了整套设计的重心：钱的状态必须始终与煤炉实际一致。

## 决策

### §1 两系统分工：ruoyi 管人和钱，日本服务只对接煤炉

| ruoyi（国内，阿里云） | 日本服务 mercari-gateway（阿里云东京，Python） |
|---|---|
| 用户、登录、地址、订单、支付、退款、报价锁价、商品锁、下单任务、对账、履约看板、后台 | 搜索 / 详情 / 实时查价、图片代理、准入判定所需的原始字段、账号登录态、自动下单、按商品查购买记录、交易状态巡检 |

日本服务里**不存任何用户个人信息**，只认得「订单号、商品 ID、锁定日元价」。它挂了、被封、被改版，
拼团与支付照常，代切自动转人工。

**小程序直连日本后端不采纳**：小程序请求域名须 ICP 备案而备案要求国内接入；用户手机号 / 地址出境要走
个人信息出境评估；国内用户手机到日本的线路比云厂商之间更差。

### §2 调用方式：ruoyi 同步调用，下单幂等，结果三态

- **ruoyi → 日本服务单向同步调用**（HTTPS + HMAC 签名 + 时间戳防重放），日本服务不回调 ruoyi。
  理由：ruoyi 不必暴露一个对公网的入站端点；结果丢失时 ruoyi 主动对账即可，回调反而多一条要保证送达的链路。
  「日本服务回调 ruoyi 推送下单结果」**不采纳**。
- **支付回调里同步下单不采纳**：回调同事务只写一条下单任务（outbox），由本地调度异步执行。
  否则回调超时 → 微信重推 → 重复下单。
- **幂等键 = 订单号**（`JPO-…`，一单只含一件代切商品，REQ-SNAP-035）：日本服务每次下单前先查采购账号购买记录里有没有这件商品，有则直接返回成功。不用订单行 id —— 雪花 id 在日本服务那侧没有业务语义（领域主权表铁律 2）。
  只有这样重试才安全。
- **结果三态**：`success`（拿到煤炉交易号）/ `failed`（已售出、下架、涨价、准入不过）/ `unknown`（其他一切）。
  `unknown` **不退款、不重试**，按 30s / 2min / 10min 三次对账；仍不明转人工。
- **对账只会自动得出「成功」，从不自动得出「失败」**（Kevin 2026-10-03）：购买记录查不到时，无论商品是否还在售，
  都只排下一轮对账，满 3 轮仍查不到转人工，绝不判失败退款。理由：购买记录可能滞后，「已售出」也可能正是被我们自己买走；
  误退的钱收不回来，而结果不明本身很少见（只在超时 / 断网 / 触发验证时出现），多转几单人工的代价远小于一次误退。
  等满 3 轮而不是第一次查不到就转人工，是因为最常见的不明恰恰是「点了购买、超时、其实买到了」，购买记录需要时间刷出来。
  同理，日本服务只有在「没点『購入する』就停下」时才允许返回 `failed`，点过之后拿不到交易页一律 `unknown`。

### §3 读写技术

- **读**：网页版背后的 JSON 接口为主（mercapi 已实现 DPoP 签名，2026-10-01 东京机房 IP 实测：搜索 1.4~4.0s、
  详情 0.31s、取图 1.2s，无拦截）；接口失效时自动降级为无头浏览器渲染解析（实测搜索页 8.5s、商品页 3.5s）。
  同关键词在途请求合并 + Redis 短缓存 + 全局限速。
- **写**：Playwright 驱动常驻浏览器（持久化登录态，日本员工远程手工登录一次含短信验证），出口走固定日本
  ISP 代理，不用机房 IP。一个账号一个执行进程串行下单，浏览器常驻预热。**逆向购买接口直调不采纳**
  （逆向工作量最大、请求最不像真人、一改版全挂）。
- **App 自动化（安卓模拟器 + Appium）为备选**，仅当 S0 实测甲方账号网页版不能下单时启用。
- ★ **S0 技术验证结论回填本节**（REQ-SNAP-064）：go → 按上面执行；no-go → 自动下单降级为全部人工代买，
  §2 的任务 / 对账框架不变（人工就是一种结果来源）。

### §4 风险边界

自动下单违反煤炉规约（「弊社が提供するインターフェイスとは別の手法を用いてサービスにアクセスすること」），
后果是封号，甲方已知悉并选择接受（REQ-SNAP-006，上线前书面确认 REQ-SNAP-062）。在此之上**不再往前走一步**：

- **打码平台 / 指纹伪装 / 批量注册小号，以及任何绕过登录或验证环节的手段，一律不采纳。**
- 出现验证码 / 登录验证 / 短信验证 / 连续 3 次非业务失败 / 登录态失效 → 该账号停用、自动下单整体暂停、
  全部转人工，只能 admin 手动恢复。

理由：① 对抗没有尽头，维护成本无法估算；② 用甲方自己的账号像正常用户那样操作，属于违约、后果是封号；
绕过验证就成了绕过平台的访问控制，风险性质不同，不在甲方接受过的范围内。

### §5 订单行承载代切：source=snap + 新列，不另建订单表

ADR-0020 §4 说「二期只加一个枚举值 `snap` + 一条字典数据，表结构一律不动」——**这句话收窄**：
`gz_jp_order_item.product_id` 是 `NOT NULL` 且语义为 `gz_jp_product.id`，代切行没有拼团商品可指。
**Kevin 2026-10-03 设计门确认**：新迁移 `ALTER gz_jp_order_item` —— `product_id` 改可空、加 `snap_item_id`（可空），
应用层保证 `source=batch ⇔ product_id 非空`、`source=snap ⇔ snap_item_id 非空`。
同理 `gz_jp_refund` 的唯一键由 `(tenant_id, order_item_id)` 改为 `(tenant_id, order_item_id, refund_type)`（新列 `refund_type`：`purchase_failed` / `shipping_diff`，存量行回填 `purchase_failed`），让到付差价退款与之后可能的失败退款共存。
订单表、退款表、履约状态机、履约看板仍是一套，这是 ADR-0020 §4 预留 `source` 维度要保住的东西。「另建代切订单表」**不采纳**（履约看板与对账要查两套表）。

## 后果

- 正面：钱的正确性只依赖 ruoyi 一侧的状态机 + 对账，日本服务可整体替换（换成官方 API、换 App 自动化）而业务代码不动。
- 负面：同步调用让 ruoyi 的下单执行线程占用最长 45s —— 用独立线程池，与 Web 请求线程隔离。
- 持续成本：煤炉改版会使读 / 写失效，一年可能多次；靠 REQ-SNAP-044 主动探测发现，修复工时是持续性成本。

## 复活条件

- 煤炉官方合作谈成 → §3 读写换官方接口，§1 §2 不变；§4 风险边界自然解除。
- 订单量证明人工代买占比长期 > 50% → 重新评估自动下单的投入产出。
