# GZ-BEAN-059 — 桌型使用时长 · 上桌率（月度）

> 关联：ADR-0016（坐席模型：mp 顾客选桌型档不选座）/ ADR-0024 §1 §3（桌型级「今天关几个」= 报表分母的唯一真源）
> 权威：`doc/11` §3.3 座位单元 · §3.4 桌型配置 · `doc/daily/D27/README.md`（需求提炼）
> 需求原文：2026-09-28 甲方微信 ——「因为线下店员没有去填现金，从后台的看板帮我统计一下每一种座位的上桌率，
> 用于我之后店内调整」，追问后：「我想知道每个月 单人桌 双人桌 六人桌 分别坐了多少小时」

## What

「拼豆营业额」页（`/gz-bean/revenue`）新增**只读**区块「桌型使用时长 · 上桌率」：
按 **月份 × 门店 × 桌型档** 列出 **① 这个月一共坐了多少小时**、**② 该桌型的每个座位（整桌桌型 = 每张桌）平均坐了多少小时**、
**③ 桌数/座位数**（②的分母，摆出来让甲方能自己验算），再带可售/营业时长、两个比率与单数分布（总/已上桌/未到店/已取消/含包天）。

**不含任何金额列** —— 甲方明确说店员不填现金，金额天然少算（本页上方的营业额卡片继续保留，两者口径独立）。

> **② 是甲方真正要的那两个数之一，第一版漏了**（Kevin 2026-09-28 追问打回）：
> 「小程序里只能看到桌型，具体座位是店员自行分配的，所以甲方想要的应该是**每种桌型分别做了多少小时**
> ＋**每个桌型的座位平均做了多少小时**」。第一版只给了总时长 + 一个上桌率百分比 ——
> 百分比是我为了"能横向比"自己加的，甲方要的是能直接对照的**绝对量**（"我的单人桌一个月平均才坐 6.3 小时"）。
> 现在 ① ② ③ 并排，上桌率降为归一化视图（它唯一不可替代的用途是比"30 天的月"和"28 天的月"）。

## 口径（逐条钉死，改任何一条都算商业口径变更）

| 项 | 定义 | 实现锚点 |
|---|---|---|
| 时长单位 | **桌·小时 / 座·小时**（`whole` 按桌、`seat` 按座），与 `slotCapacity()` 同量纲 | `GzBeanSeatTypeConfig.slotCapacity()` |
| 营业格 | `GzBeanHourSlotResolver.selectEnabledSlotsForDate(storeId, date)` 当天的小时格（午休缺口不算） | 与看板抽屉同一集合 |
| **上桌时长**（分子） | Σ 每张**已上桌**单覆盖的**营业格数**：`status IN ('used','completed')` 且 `pay_status='paid'` 且 `del_flag='0'`；「覆盖」= 格起点 `gi` 落在 `[slot_start, slot_end)` 内（`coveredSlots`） | `GzBeanRevenueServiceImpl.SEATED_STATUSES` / `coveredSlots` |
| **可售时长**（分母 A） | Σ 每格 `有效容量 = slotCapacity − 当日生效关闭数`；**与小程序可卖量同源** | `GzBeanSeatTypeConfig.effectiveCapacity`（经 `effectiveCap(config, recordedClose)`） |
| **营业时长**（分母 B） | Σ 每格 `slotCapacity`（不看关闭） | 同文件 |
| **桌数/座位数** | 该桌型档容量 = `slotCapacity()`（`whole` = 桌数 / `seat` = 座位数）—— **平均值的分母**，摆出来让甲方能自己验算 | `capacityPerSlot` |
| **平均每桌/每座时长** | `上桌时长 ÷ 桌数(座位数)` = 「每个座位（整桌桌型 = 每张桌）平均坐了多少小时」。整桌桌型一次预订即整桌座位都在用，故「平均每桌」与「平均每座」是同一个值 | `avgHoursPerUnit` |
| **来源拆分** | `上桌时长` 按 `gz_bean_booking.source` 再拆两段：**小程序** = `mp`（列默认值）；**线下** = `walk_in`（看板现金入座）+ `admin`（后台代客）。**两段相加恒等于上桌时长**（单测 + E2E 双守卫） | `mpHours` / `offlineHours` / `offlineBookings` |
| **容量起算日** | 容量只统计 **`桌型.create_time` 之后**的日子（create_time 为空的老 seed 行视为一直存在）。今天新建的「六人桌」不会在过去几个月里显示成「上桌率 0%」 | `GzBeanRevenueServiceImpl` 日循环里的 `cfgBorn` 夹取 |
| 上桌率 | `上桌时长 ÷ 可售时长`（回答「敢卖的格卖掉了多少」）；同一件事的百分比视图，唯一不可替代的用途是横向比天数不同的月份 | `occupancyRate` |
| 营业占用率 | `上桌时长 ÷ 营业时长`（回答「开着门的格用了多少」） | `openOccupancyRate` |
| 分母为 0 | 返回 `null`，前端 `—`；**绝不返回 NaN/Infinity** | `rate(...)` |
| 合计行 | 比率**按合计重算**，不求和各行百分比；**「桌数/座位数」与「平均每桌/每座时长」给「—」** —— 桌与座不是同一单位，跨桌型相加/求平均没有业务含义 | `usageSummary()` |
| 包天单 | 按**当天营业格数**（如 11）计，不按钟表 12h；`is_day_pass=1` 单独计数 | `coveredSlots` + `dayPassBookings` |
| 组单 | 每张子单各计一次（N 座 → N 座·小时），自然累加 | 逐 `gz_bean_booking` 行 |
| 门店维度 | owner 可看全部门店（`storeId` 空 = 全部，出「门店」列）；staff 强制本店 | 控制器 `staffStoreId` |

**为什么给两个分母**：只给上桌率，甲方无法区分「卖不动」与「关着不卖」；而「关着不卖」正是 ADR-0024 引入的动作。
两列并排就能一眼分开这两种情况。

## AC

### A. 数据正确
- AC1：`GET /system/gz/bean/revenue/seat-usage?startDate&endDate&storeId` 返回 `month × 门店 × 桌型档` 行；空区间返回空数组不报错
- AC2：上桌时长只由**时段 + 状态 + 收款状态**推出，**完全不读 `amount_cent`**（金额列不出现在 VO/SQL 里）
- AC3：分母与小程序可售量同源 —— 同一 (门店, 桌型, 日期, 格) 下，`可售时长` 的每格容量 == 看板抽屉 `GET .../day-sellable` 的该格 `remaining + 已订` 口径
- AC4：`mp_long_close_count` 与 `gz_bean_slot_quota_close` 按 **ADR-0024 §6 覆盖关系**参与：当日有记录则用当日值，无记录才用长期值；两者**不相加**
- AC5：比率分母为 0 → `null`；前端显示「—」，页面文本不含 `NaN` / `Infinity`
- AC6：合计行的比率为合计重算值，**不是**各行百分比之和
- AC7：租户隔离 —— 所有 SQL 带 `tenant_id`；staff 只见本店（即使显式传别家 `storeId`）

### A1b. 门店 / 桌型 都是**筛选**（Kevin 2026-09-28 第三轮）
- AC0a：**门店筛选必选、且不含「全部门店」**（本报表按"一家店一个店地看"；全部门店会把同一月份渲染成多段，被读成"两个月 4 月"）
- AC0b：表格里**不再有门店列**（门店已是筛选条件）；默认落第一家门店，首屏不发 `storeId=null` 的请求
- AC0c：区块标题旁加**桌型筛选**（默认「全部桌型」；选项取本区间实际出现的桌型，自定义桌型自动出现）
- AC0d：桌型筛选只影响本区块（不改上方金额区块）；切换后**合计行只算筛选后的行**；换区间后若原选中桌型不再出现 → 自动回到「全部桌型」
- AC0e：默认顺序 = **月份 → 桌型**（月份单调不减）；同月单元格 rowspan 合并
- AC0f：新建桌型的容量**只从创建日起算** → 该桌型在更早的月份不出行（而不是显示 0% 上桌）
- AC0g：数值列可点表头排序；`sortable="custom"` 由页面自己排 `:data`（内置排序会让 rowspan 合并错位，`pitfalls.md` §8.17）

### A3. 线下现金入座要能和小程序分开看（甲方 2026-09-29 追加）
> 甲方原话：「这里面有个漏洞 就是他们**现金入座的没有写金额**」「但是**也需要参与统计**」。
> 核查结论：**线下单一直计入统计** —— 分子只看 `status IN ('used','completed')` + `pay_status='paid'`，
> 既不筛 `source` 也不读 `amount_cent`（金额从来没进过这个报表）。甲方要的是**把口径显性化**，所以拆成两列。

- AC1f：新增「**小程序时长**」（`source='mp'`）与「**线下时长**」（`walk_in` 看板现金入座 + `admin` 后台代客）两列，
  位置紧贴「上桌时长」之后，形成对比；**两列相加恒等于上桌时长**（每一行、合计行都要成立）
- AC1g：新增「**线下单数**」列（其中线下单的笔数）—— 现金常常没录金额，甲方要靠单数和钱箱对账
- AC1h：线下时长/单数**有值时给醒目色**（一眼看出本月有没有线下生意）
- AC1i：口径说明必须写清「线下入座**一直计入**统计，只是以前混在一起看不出占比」
- AC1j：**金额仍然不参与**本报表（`amount_cent` 不进 SQL / VO）—— 甲方说的"没写金额"影响的是营业额卡片，不是这张表

### A2. 甲方要的两个数（2026-09-28 追问后补，第一版漏了第二个）
- AC1b：区块必须同时给出「**上桌时长**」（该桌型这个月一共多少小时）与「**平均每桌/每座时长**」（每个座位/每张桌平均多少小时）
- AC1c：平均值必须**能用页面上的两个数验算出来** = 上桌时长 ÷ 桌数(座位数)（所以容量列必须显示，且带 `桌`/`座` 单位）
- AC1d：平均值与容量列的**合计行给「—」**（混量纲不可加），不是 0、不是空串、不是"平均值的平均"
- AC1e：容量为 0 的桌型 → 平均值 `null` → 页面「—」（不许出现 `Infinity`）

### B. 页面
- AC8：「拼豆营业额」页在「桌型×计费方式拆分」与「明细」之间新增区块「桌型使用时长 · 上桌率」，跟随页面既有的**日期区间 / 门店筛选**一起刷新（不新增筛选控件）
- AC9：列 = 月份 / 桌型（带 `桌`/`座` 量纲标签）/ **桌数/座位数** / 上桌时长 / **小程序时长** / **线下时长** / **平均每桌/座时长** / 可售时长 / 上桌率 / 营业占用率 / 总单数 / 已上桌 / 未到店 / 已取消 / 含包天 / **线下单数**
- AC10：桌型列标注量纲（`座` / `桌` 标签），时长的单位在**口径说明**里写清（「桌·小时 / 座·小时」）
- AC11：区块下方必须有**口径说明**（含「平均每桌/座时长 = 上桌时长 ÷ 桌数(座位数)」「上桌率 = 上桌时长 ÷ 可售时长」「合计按合计重算、混量纲给 —」「与金额无关」），甲方与店员不需提问即可自行理解
- AC12：未到店数 > 0 标警示色（甲方拿它判断客人爽约）
- AC13：中英文双语 key 齐全（`zh_CN` / `en_US` key 数相等）
- AC14b：**门店筛选改必选会连带影响本页其它区块**（汇总卡 / 拆分 / 明细 / 趋势都变单店口径）—— 本 ticket 的**已知取舍**；
  后端仍支持 `storeId` 为空（保留"全部门店"能力，只是页面不给入口）。恢复全店口径 = 把清空 + 全部选项加回来，纯前端改动

### C. 零回归
- AC14：**无 DDL、无新菜单、无新权限**（复用 `gz:bean:revenue:list`）；老接口与看板读写路径一行未动
- AC15：`selectUsageRowsInRange` 只取时长所需列（不拉 `verify_code` / `dedup_token` 等大字段）；关闭记录一次查完，不做 N+1

## 验证

- **L1 独立 SQL 对账（真库，含来源拆分）**：门店1 2026-07 已上桌 **45 格·小时 = 小程序 33 + 线下 12**（8 张 walk_in 单），
  与端点返回逐条一致；页面显示 单人 19=18+1 / 双人 24=14+10 / 四人桌 2=1+1。
- **L1 独立 SQL 对账（真库，含平均值）**：`avg = used_hours / cap` 独立算出 `5.0 / 0.3 / 6.3 / 6.0 / 0.3`，
  与页面 `toFixed(1)` 逐条相等（`0.25 → 0.3` 两边同口径）。
- **L1 独立 SQL 对账（真库）**：用递归 CTE 从 `gz_bean_time_slot_template` 自造营业格，
  连 `gz_bean_booking` + `gz_bean_slot_quota_close` + `gz_bean_seat_type_config.mp_long_close_count`，
  独立算出 2026-04-01～2026-09-28 × 2 店 × 3 桌型的「上桌 / 可售 / 营业」→ 与端点返回 **36 行逐字相等**。
  含两个关键手算校验：① 四人桌 2026-07 `可售 2046 = 2728 − 长期关闭 2 × 11 格 × 31 天`；
  ② 四人桌 2026-09 `可售 1859 = 27 天×11×(8−2) + 09-27 的 11×(8−1)` —— **当日覆盖长期**（7 而非 5）。
- **L0 单测**：`GzBeanRevenueServiceImplTest` **21/21**（含「时长按来源拆 + 两段相加 = 总时长」「容量只从桌型创建日起算」「月份优先于门店」）（新增 6 条：分子只认已上桌 / 包天按营业格 / 分母 0 给 null /
  合计重算 / 长期与当日覆盖 / **平均每座时长（含容量 0 → null 而不是 Infinity）**）；模块合计 **326/326** 绿。
  **变异验证**：把分子改成钟表时长 → 2 条用例变红。
- **L2 真栈 E2E**：`plus-ui/e2e/gz-bean/seat-usage.spec.ts` —— 页面渲染行与端点返回**逐字比对**（含门店维度、
  36 行全覆盖）；**容量列 = 数字+单位**、**平均列 = 后端 `avgHoursPerUnit` 保留 1 位且 = 上桌时长 ÷ 容量**；
  合计行的容量/平均值必须是「—」；口径说明可见；比率无 `NaN`；分母 0 显示「—」；
  **门店筛选无「全部门店」选项且已选一家、表里无门店列、桌型筛选后行数与合计行随之变化、排序后首行 = 最大值**、
  **小程序时长/线下时长逐行与后端一致且相加 = 上桌时长（含合计行）**。
- 前端门：`eslint` 0 / `vue-tsc` 无新增 / `pnpm build:prod` exit 0。

## 不做

- **导出 Excel**（甲方没提；真要再单开）。
- **按物理座位逐座统计**（哪个座位被坐了多少小时）：mp 顾客不选座、座位由店员现场分配（ADR-0016），
  所以「每个座位平均时长」= 总时长 ÷ 该档容量（本 ticket 给的就是它），而不是按 `gz_bean_seat` 逐座统计。
- **改看板/售卖逻辑**：本 ticket 纯读路径。任何影响 GMV / 售卖量的动作都不在范围（硬约束 14）。
