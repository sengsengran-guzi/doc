# D27 — 拼豆营业额页补「桌型使用时长 · 上桌率」

> 需求来源：**2026-09-28 甲方微信 + 截图**（不在 `doc/test/kevin-test.xlsx` 里，属新需求不是 bug）：
> 「这个拼豆营业额这里 能不能优化一下 因为线下这个 店员他们没有去填现金
> 从后台的看板 帮我统计一下**每一种座位的上桌率** 用于我之后店内调整」
> 追问后的目的原话：「我想知道 **每个 月 单人桌 双人桌 六人桌 分别坐了多少小时**」

## 需求提炼

甲方要的东西只有一句：**「哪种桌子、哪个月、到底被坐了多少小时」**，用来决定店里怎么排/加不加桌。
两条硬约束是从他话里读出来的：

| 线索 | 读出来的约束 |
|---|---|
| 「店员没有去填现金」 | **金额不可信也不能用** —— 线下收现没落库，营业额天然少算。报表必须**纯靠时段/状态**算出来，不许出现任何金额列，也不许把金额当权重 |
| 「用于我之后店内调整」 | 要能**横向比较**不同桌型（单人桌 vs 六人桌），所以不能只给绝对小时数，必须配一个「占了多少可卖的量」的比率 |
| 「每一种座位」 | 维度 = **桌型档**（`gz_bean_seat_type_config`），不是物理座位；甲方嘴里的「座位/桌」是同一个东西的两种叫法 |

**结论**：在既有「拼豆营业额」页（`/gz-bean/revenue`）里加一个只读报表区块 —— 不新建页面、不新建菜单、不新增权限。

## 追加（2026-09-29 甲方微信）

> 「这里面有个漏洞 就是他们**现金入座的没有写金额**」「但是**也需要参与统计**」

**核查**：线下（看板现金入座 `walk_in` / 后台代客 `admin`）的单**一直计入**上桌率 —— 分子只看「已上桌 + 已收款」，
不筛来源、不读金额。所以这条不是漏算，是**口径不透明**：混在一起看不出线下的占比。
**处理**：`上桌时长` 按来源拆成「小程序时长」「线下时长」两列（相加恒等于总时长），另给「线下单数」供现金对账。
「没写金额」影响的是**营业额卡片**（`amount_cent=0` 的现金单按 ¥0 计，GZ-BEAN-046 刻意"不臆造收入"），与这张表无关。

## 口径（本批的核心，全部在 ticket 里逐条钉死）

时长量纲 = **「桌·小时」/「座·小时」**，与看板格子、`slotCapacity()` 同源：

| 项 | 口径 | 为什么 |
|---|---|---|
| 上桌时长（分子） | 每张**已上桌**单（`status IN ('used','completed')` 且 `pay_status='paid'`）覆盖的**营业小时格数**，按单累加 | 只用时段与状态，不碰金额；包天单算当天营业格数（11）而不是钟表 12h —— 与「卖了多少格」同一把尺子 |
| 可售时长（分母 A） | Σ 每格 `有效容量`（容量 − 当日关闭，未记录当日关闭则 − 长期关闭） | **与小程序能卖的量同源**（`effectiveCapacity`）。这才是「上桌率」——卖出去的格 ÷ 敢卖的格 |
| 营业时长（分母 B） | Σ 每格容量（不看关闭） | 甲方可能想问「店里明明开门了，为什么算低」→ 必须能区分「没卖」和「关了不卖」 |
| 合计行 | 比率**按合计重算**，不是把各行百分比相加 | 相加是这类表最经典的错 |
| 分母 0 | 返回 `null` → 前端显示「—」 | 不许出现 `NaN` |

**两个分母都给**，因为它们回答的不是同一个问题：可售率跌 = 我们主动关了很多格（或卖得差），营业率跌 = 生意就是差。
只给一个的话甲方一定会追问另一个。

## 与看板的关系

- **看板不变**：这次只加读路径，`selectBoard` / 核销 / 分座 / 放座 / 延时一行未动。
- **但口径必须同源**：报表「今日关闭」用的是看板抽屉同一张 `gz_bean_slot_quota_close` 与同一个
  `effectiveCapacity` —— 报表显示 100% 已卖、抽屉却显示还有空位，是最伤信任的一类不一致。

## 验证（真栈 + 独立 SQL）

- **独立 SQL 对账**：用递归 CTE 从 `gz_bean_time_slot_template`（营业窗口）自造营业格，
  连 `gz_bean_booking`（已上桌单）+ `gz_bean_slot_quota_close` + `gz_bean_seat_type_config.mp_long_close_count`，
  独立算出全部 6 月 × 2 店 × 3 桌型的「上桌 / 可售 / 营业」三列，与端点返回**36 行逐字相等**。
- **E2E**：`plus-ui/e2e/gz-bean/seat-usage.spec.ts` —— 页面渲染的行与端点返回逐字比对（含门店维度）+ 口径说明可见 + 比率无 `NaN`。
- 对账中一度出现「双人 7 月 SQL 23 vs 报表 24」的差异，查实是**我的 SQL 参照写错**（用 `HOUR()` 截断，
  实现是「格起点落在单时段内」）。这条例证留着：**自造对照只有口径逐字对齐才有判定力**（见 `pitfalls.md` §8.13）。

## 不在本批

- **不做导出 Excel**：甲方要的是「店里调整」的决策依据，页面上能看就行；真提了再单开（估计 S）。
