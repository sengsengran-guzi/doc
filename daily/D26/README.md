# D26 — 看板计时格与桌型配置对不上

> 需求来源：2026-08-31 甲方微信 + 截图两条：
> ①「我明明在座位里添加了 2 个 4 座临时桌，但是在看板页面却还是只有 4 个座位」
> ②「四人桌只有 2 个，看板里却显示 12 个座位，为什么，这里的逻辑似乎都不对」

## 本批 ticket

| Ticket | 内容 | 复杂度 |
|---|---|---|
| `GZ-BEAN-055` | 配额 ↔ 计时格错配：可见化 + 同步（补齐 / 安全缩减）+ 三道守卫 | M |

## 根因（一句话）

**「这个桌型有几个座」在系统里有两个各自独立的计数器，只在店员手点「批量生成」那一刻对齐过一次。**

| 谁 | 算法 | 何时变 |
|---|---|---|
| 小程序每小时能卖几个（`slotCapacity()`） | `数量 × 每桌座位数` **现算** | 改表单里的「数量」→ **立刻生效** |
| 看板几个计时格 / 能分几个座（`selectBoard`） | `gz_bean_seat` **实际行数** | 只有点「批量生成」才变 |

`GzBeanSeatTypeConfigServiceImpl` 全文**没有一行**碰座位表 → 改数量永远不动座位。
`batchGenerate` 的 `upsertSeatUnit` 只做插入 / 复活 / 跳过 → **只增不减**。
「要不要生成计时格」的弹窗只在 `isAdd` 时触发 → **编辑路径完全没有出口**。

→ 症状①：临时桌建时数量 1（生成 `T11-1..T11-4`），后改成 2，编辑不弹窗 → 没有 `T12-*`。
→ 症状②：四人桌数量 2 只该有 `Q1/Q2` 共 8 格；看板 12 格 = 曾按 3 生成过，数量调回 2 后多的不会被删。

ADR-0016 取舍 C 已写明这个不变量（`slotCapacity` 必须 = 可分物理座位数），
选的执行方式是「构造即一致 + 人工同步」——**人工同步这条链断了**（编辑不提示 / 缩减不清理 / 后台看不出）。

## 后果（不是显示问题）

| 方向 | 后果 |
|---|---|
| 配额 > 座位 | 小程序卖得出，核销时店员**没座可分**，客人已付款 |
| 配额 < 座位 | 看板那些格子**线上永远卖不掉**，只能走代客。四人桌当时就是这种 |
| 临时桌（不上小程序） | 纯粹是看板少格子，正好砍掉 GZ-BEAN-054 一半价值 |

本地 dev 库当场抓到同款：「单人」数量=1 但看板 8 格，`availability/detail` 实测每时段 `opened:1` ——
**摆着 8 个格子，小程序每小时只肯卖 1 个**。

## 顺带修掉的两个既有 bug

1. **删/停用座位零守卫 + 看板丢孤儿单（事故级）**：`selectBoard` 是「遍历座位 → 取该座的单」，
   ②待分座区只收 `seat_id IS NULL` 的单 → 移除一个还挂着单的座位，**那笔已付款单从看板上彻底消失**。
   而 `deleteByIds` 是裸的 `baseMapper.deleteByIds(ids)`，今天在页面上点删除就能触发。
2. **软删座位永远复活不了**：代码判 `del_flag == "2"`，全局 `logicDeleteValue` 其实是 **1** →
   复活分支**从来没触发过**；而 `uk_tenant_store_seat_no` 不含 `del_flag`，编号被永久占住 →
   **删过的座位再也生成不回来，界面还显示「生成 0 个」不报错**。真库实测复现（同步 2→2、created=0）。

## 做法（甲方 8-31 二次反馈后重做）

第一版做成了「列表显示 `4 / 8` + 一个『同步计时格』按钮」——甲方一句话打回：
**「我感觉搞复杂了，员工都不会使用了；桌子和座位应该和看板上对应才对吧」**。他是对的：
那等于把系统内部的不一致外包给店员，让他们去理解「配额」「计时格」两个概念再手动对齐。

重做为**店员只填一个数**：

| 变化 | 说明 |
|---|---|
| 「计时格 4 / 8」→「看板格数 8」 | 一个只读数字，就是这个桌型在看板上占几个格 |
| 删掉「同步计时格」按钮 | 保存桌型时后端自动对齐座位，店员不需要知道有这一步 |
| 删掉新建后「要不要生成计时格 + 填前缀」弹窗 | 新建即自动生成，编号前缀后端自己挑不撞号的 |
| 减少格子时确认一次 | 唯一保留的打扰：撤格子是破坏性的，要让人知道 |
| 对不齐 → **整单回滚** | 宁可保存失败，也不存下「配置说 8、看板只有 6」的自相矛盾配置 |

`POST /seat/sync/{id}` 端点与前端 API 一并删除（没有调用方了）；同步逻辑保留在 service 内部供保存时调用。

真浏览器验的四件事：
1. 列表只有一个「看板格数」数字，全表**搜不到「同步计时格」**字样
2. 历史错位（数量 3 / 看板 8）→ 只点「编辑 → 确定」→ 自动变 3 / 3，**没点任何按钮**
3. 减格子弹确认：「看板会从 8 个减少到 4 个（撤掉 4 个）…」
4. **挂着预约时整单回滚**：报 `Q2-4 还挂着今天及以后的预约…请先在店内计时看板上把这些客人改派`；
   查库确认 `quantity` 仍是 2、8 个座位全在（同步已撤掉的 3 个也被回滚回来），**没有半应用状态**

## 未做（需甲方拍板）

**方案 A「座位行成为唯一真源」没做** —— 那会改变线上每小时实际卖几个座（四人桌 8→12、单人 1→8），
属商业口径变更不是修 bug。现在的模型是：**数量是店员填的唯一输入，座位和看板都自动跟它走**。

## 无迁移

本批**零 DDL、零新菜单、零新权限**（同步复用 `gz:bean:seat:batchGenerate`）。
