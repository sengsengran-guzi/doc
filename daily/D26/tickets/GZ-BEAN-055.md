# GZ-BEAN-055 — 配额 ↔ 计时格对齐（可见化 + 同步 + 守卫）

> 关联：ADR-0014 §2（配额分母）/ ADR-0016 取舍 C（配额必须 = 可分物理座位数）/ GZ-BEAN-054（临时桌）
> 权威：doc/11 §3.3 座位单元 · §3.4 桌型配置

## What

让店员**只填一个数**（「这个桌型我店里有几张桌」），看板格子和小程序售卖量都自动跟着它走 ——
店员不需要知道系统里还有第二个计数器，也不需要点任何「同步」。
对齐过程**绝不让任何已付款的单从看板上消失**。

> 第一版做成了「显示 `4 / 8` + 同步按钮」，甲方打回「搞复杂了，员工都不会使用」。
> 那是把系统内部的不一致外包给了使用者 —— 已重做为保存即自动对齐。

## AC

### A. 店员只面对一个数
- AC1：桌型配置列表「计时格」列显示**一个只读数字**（该桌型在店内计时看板上占几个格），
  **不显示 `实际 / 应有` 两个数**、**不提供任何同步按钮**
- AC2：保存桌型时后端**自动**把座位单元对齐到「数量 × 每桌座位数」——新建也自动生成，
  店员不需要填编号前缀（后端自己挑不与已有座位撞号的前缀）
- AC3：仅当保存会**减少**看板格子时确认一次（撤格子是破坏性的）；加格子不打扰
- AC4：历史错位（本次上线前就存在的，或有人直接去「座位单元」页删了座位）→ 数字标警示色，
  tooltip 只说「保存一次该桌型即会自动对齐」，**不要求店员理解「配额」这个概念**

### B. 对不齐就整单回滚
- AC5：自动对齐没能达到目标数量（多余座位挂着预约 / 编号被别的桌型占）→ **抛异常回滚整个保存**，
  配置不落库。理由：存下一个「配置说 8、看板只有 6」的配置，正是本 ticket 要消灭的东西
- AC6：报错必须点名卡在哪几个座位 + 指明去哪儿处理（店内计时看板改派），否则店员只会反复点保存
- AC7：只在数量类字段真的变了、或已有错位时才动座位 —— 改价格 / 改名字不碰座位表
  （否则会出现「因为某个座位挂着预约，连改价都保存不了」）
- AC8：停用的桌型不生成座位（它的座位本就不上看板）

### C. 守卫（三道）
- AC9：**移除守卫** —— 删除 / 停用 / 同步缩减三条路径共用：座位仍挂**今天及以后**的活跃单
  （`status IN ('pending','used')` × `pay_status IN ('paying','paid')`，与 `selectActiveBookingsForBoard` 逐字一致）
  → 删除/停用**拒绝并点名座位编号**；同步缩减**跳过该座并回报**，不因一个受阻放弃整批
- AC10：**订法守卫** —— 桌型已生成座位单元时禁止改 `bookMode`
  （整桌 `S1` 与按座 `Q1-1` 编号规则不同，改了会让同步把整批判成多余）
- AC11：**复活守卫** —— 软删座位必须能被复活，判定按「非未删值即已删」，
  不依赖任何写死的删除值（原代码判 `"2"` 而全局是 `1`，分支从来没触发过）

### D. 零回归
- AC12：无 DDL、无新菜单、无新权限
- AC13：桌型配置列表 / 详情新增派生字段不影响既有调用方；一次 group by 回填，不 N+1

## 不做

**方案 A「座位行成为唯一真源」（`slotCapacity()` 改成数实际座位行）不在本 ticket。**
它会改变线上每小时实际售卖量（四人桌 8→12、单人 1→8），属商业口径变更，需甲方书面确认；
且会引入「新建桌型忘了生成座位 → 配额 0 → 小程序静默显示约满」的新故障模式。
